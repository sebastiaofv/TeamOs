The file at a glance

A board file is a complete document for one project: its metadata, current columns and tasks, display title, and optional extensions. The current state lives in board; historical snapshots and events live separately in extensions.timeline. A portfolio loads several of these documents; its runtime project IDs are not board-file IDs.

This reference describes the implementation in src/legacy/main.js and src/domain/, inspected on 11 September 2026. Schema version is 1 and the application identifier is teamos-kanban. All examples are synthetic. This HTML is self-contained and can be shared or printed without an internet connection.

Import is not a lossless round trip. Validation checks whether input is accepted. Normalization then changes some accepted values or drops fields. “Required” below means required on import; “written” describes the current serializer.

Use a filename such as release.board.json. The README recommends *.board.json, but the current code checks the broader .json suffix. Both names work. Use standard JSON: double quotes, no comments, no trailing commas, and no JavaScript-only values such as undefined.

Metadata and board settings

FieldType / valueMeaning and behavior
meta.schemaVersionnumber: 1Required, exact numeric value. The string "1" is rejected here.
meta.appIdstring: "teamos-kanban"Required; exact and case-sensitive.
meta.createdAttimestamp stringDocument creation time. Preserved when it is a valid string timestamp.
meta.updatedAttimestamp stringDocument update time. Serializer replaces it with the current time; this does not mean every task changed.
board.settings.titlenon-empty stringHuman-readable project name. Trimmed on serialization. It is not a unique identifier and need not match the filename.

Use ISO 8601 timestamps with a timezone, preferably UTC: 2026-09-11T09:00:00.000Z. Task and event timestamp validation accepts any non-empty string understood by JavaScript Date.parse; it does not enforce this exact ISO spelling. Metadata validation is looser still: it calls Date.parse without a string-type check. Write strings consistently, since serialization only preserves valid string timestamps. Dates without a time use YYYY-MM-DD. No validator checks that creation precedes update.

Columns, status, and order

Stored statusDefault visible titleMeaning
backlogbacklogIdeas and work not yet scheduled.
to-doto-doReady or planned work.
doingin progressWork underway. Store doing, not the display title.
donedoneCompleted work.

Each column has exactly two non-empty string properties: status and title. Status values must be unique on import, and every task’s status must exactly match a declared column status. Titles are display labels; changing a title does not change task status. Column array order controls display order.

The validator accepts 1–5 columns and does not restrict their status names to the four built-in values. The normalizer does: unknown columns are dropped, duplicate normalized statuses are collapsed, and if none survive the default four are restored. Unknown task statuses become backlog. For reliable files, use the four canonical statuses above.

Accepted normalization aliasesCanonical output
todo, nextupto-do
inprogress, in-progressdoing
concluiddone

Normalization trims and lowercases status strings. Before normalization, task/column matching is exact, so an alias in a task still needs a matching input column. The string in progress is a label, not a recognized alias. Task array order is preserved by serialization; there is no saved task position or order field. Checklist order is also array order.

Every task field

A task may contain only the required and optional keys below. Unknown task properties are rejected, so do not put arbitrary custom fields directly on tasks. All ten required fields must be present even when their value is empty or null.

Required on import

idfinite numberStable task identity. Use unique safe integers per board. The app commonly generates time-based IDs; import does not enforce uniqueness, positivity, or integer precision.
titlenon-empty stringMaximum 80 JavaScript string code units. Whitespace-only rejected; surrounding whitespace is not trimmed by the serializer.
descriptionstringFree-form task details; empty string is valid.
checklistarrayUse [] for none. See nested records below.
archivedbooleantrue hides the task from active views. Archiving does not remove the task or change its status.
createdAttimestamp stringTask creation time.
updatedAttimestamp stringLast recorded task update; preserved by serialization rather than refreshed for every save.
dueDatestringExact YYYY-MM-DD or "" for none. Date-only, with no timezone.
prioritystring or nullExactly high, medium, low, or null.
statusstringMust exactly match an input column’s status; use a canonical status.

Optional on import

The normal saved task contains all required fields plus assignees, tags, effort, blocked, blockerReason, attachments, phaseId, milestoneId, sprintId. Neither legacy assignee nor statusChangedAt is written. null is only the empty value for priority and effort; use "" for due dates and roadmap references, and [] for lists.

Checklists and embedded attachments

Each checklist entry has exactly text (non-empty string) and done (boolean). There is no checklist item ID. Saving trims text; reordering entries changes their order in the array. Checklist completion and task status are separate values.

Checklist array
[
  {
    "text": "Review requirements",
    "done": true
  },
  {
    "text": "Verify release package",
    "done": false
  }
]

Each attachment must contain exactly the seven properties below. These are embedded file contents, not filesystem paths or remote URLs.

mimestringMIME type, e.g. text/plain or image/png. Empty string accepted; trimmed on save.

dataUrlstringMust start with data:. Typically data:text/plain;base64,SGVsbG8=; this example encodes “Hello”. Import only checks the prefix, not full payload validity.

Base64 encoding increases document size, and historical snapshots can retain copies of attachments. Sharing the JSON shares those embedded contents, including contents retained in history. The file picker skips duplicates using normalized filename, MIME type, and size; JSON import does not enforce that duplicate rule.

Roadmap extension

extensions.roadmap is optional. If supplied, it has exactly version, milestones, phases, sprints; all three arrays are required even when empty. The intended version is numeric 1; this extension’s validator also accepts values for which Number(version) === 1, then writes numeric 1.

CollectionExact item fieldsMeaning
milestones[]id, title, dueDateA named point in time.
phases[]id, title, startDate, endDateA named period of work.
sprints[]id, title, startDate, endDateA named iteration or execution period.

IDs and titles must be non-empty strings and are trimmed. IDs must be unique within each collection after trimming. Dates must be non-empty strings with the YYYY-MM-DD shape; surrounding whitespace is trimmed. Extra item properties are rejected. Import checks the date shape only, not calendar validity or start/end ordering; authors should supply real dates with startDate ≤ endDate.

Task references connect one task to at most one phase, one milestone, and one sprint independently. Many tasks can share each roadmap item. No phase-to-sprint or phase-to-milestone parent relationship is stored. References are trimmed on save. When a valid roadmap exists, a reference to a missing ID is cleared to "". When no roadmap exists, non-empty references are preserved but do not identify an actual roadmap item.

Roadmap extension value

  "milestones": [

Timeline extension and event records

extensions.timeline stores optional history. A new empty board can have extensions: {}. When timeline recording begins, the app first captures a baseline before appending changes. Do not infer that a missing timeline means nothing happened: it means the file provides no recorded history.

FieldCanonical typeRules / meaning
versionnumber: 1Like roadmap version, accepted through numeric conversion and written as 1.
baselineEventIdstringID of the first baseline event. Empty or missing values fall back to the first event ID. Write it explicitly.
eventsarrayRequired; [] is accepted. Non-empty history must start with board.baseline, and normalized baselineEventId must match that first event ID.

Timeline normalization does not require exact keys: unknown timeline-level and event-level properties are dropped. Events are retained in array order, not sorted by timestamp. Import does not enforce unique event IDs, chronological timestamps, or semantic agreement between events and current board state.

Event fieldRequired?Meaning / validation
idYesNon-empty string. Generated IDs have the form evt_<milliseconds>_<random>; that prefix is not validated.
atYesValid timestamp string for the event.
kindYesNon-empty string. Known kinds below; unknown kinds are accepted but not replayed.
entityTypeYesExactly board or task.
entityIdYesNon-empty string. Board events use "board"; task events use the task’s numeric ID converted to a string.
summaryNoHuman-readable text. Missing, blank, or non-string values fall back to kind.
changesNoIf present, a non-empty object mapping fields to objects containing both before and after. Values can be any JSON values. Extra keys in each change are discarded.
snapshotNoIf present, a non-null object, not an array. Semantics depend on kind. Import does not recursively validate it as a board or task.
metaNoIf present, a non-null object, not an array. Event-specific metadata; not the document’s meta object.

A generated board snapshot has the normal document shape but excludes extensions.timeline to avoid recursive history. A generated task snapshot contains the normalized task record. The event validator does not require the payload needed to replay a particular kind; a “valid” event can therefore still provide incomplete history.

Event kinds and reconstruction

kindPayload generated / supportedReplay effect
board.baselinesnapshot: board documentFirst event supplies initial state.
task.createdsnapshot: new taskReplaces any same-ID task, then appends the snapshot.
task.deletedsnapshot: deleted taskRemoves matching task by entityId.
task.updatedchangesApplies each after value to the matching task.
task.status.changedchanges.statusGenerated when status is the only tracked field changed.
task.archived / task.restoredchanges.archivedGenerated when archived is the only tracked field changed.
board.restoredsnapshot: restored board; meta.fromEventId, meta.fromTimestampReplaces entire reconstructed state.
roadmap.updatedsnapshot: board; meta.roadmapKind, roadmapItemId, actionReplaces reconstructed state. action is create, update, or delete; roadmapKind is milestones, phases, or sprints.
roadmap.bulk-assignedmeta.roadmapKind, roadmapItemId, action, sprint, taskIdsUpserts the sprint object and sets sprintId on listed numeric task IDs. action is create-from-selection or assign-existing.
board.settings.updatedchangesReplay-supported: applies after values to settings. No matching producer was found in the current source.
board.columns.updatedchanges.columns or snapshot.board.columnsReplay-supported: replaces columns. No matching producer was found in the current source.

Task change tracking compares title, description, assignees, tags, blocked, blockerReason, checklist, attachments, archived, dueDate, priority, effort, phaseId, milestoneId, sprintId, and status. Timestamps and array-position changes are not tracked by this diff. If several fields change, the event is normally task.updated even if status or archive state is among them.

Replay diagram
Baseline snapshot → event[1] → event[2] → … → selected event
                      apply “after” values in array order

Current board.tasks ── authoritative current state
Timeline replay     ── historical reconstruction from recorded events

The app reconstructs from the first snapshot and applies later events in array order up to the selected index. Without a baseline snapshot it falls back to the current board snapshot. Unknown event kinds have no replay effect. Task timestamp changes are not replayed by the task diff, and history may omit ordering or other edits. Use current board data for present-day reporting; use the timeline only for what it actually records.

Values calculated by the app

ValueCalculation / interpretation
ScorePriority ÷ effort. Priority: high = 3, medium = 2, low = 1. Effort: XS = 1, S = 2, M = 3, L = 5, XL = 8. Either value missing → no score. Display uses two decimal places.
Example scorehigh + M → 3 ÷ 3 = 1.00. No score property is saved.
OverdueA task with a dueDate earlier than the current local calendar date, whose status is not done and which is not archived. Due today is not overdue.
Assignee identityNames are strings, not user IDs, emails, or account objects. Matching is case-insensitive in assignment filtering.
Checklist progressDerived from item done flags. No completion percentage is saved.
Portfolio project IDRuntime-only identity assigned when loading the document; not part of meta or task IDs.

Calendar dates are not timestamps. Task dueDate import checks the string pattern, not that the day actually exists. Authors should validate real calendar dates themselves. UI filters, selections, view modes, sort choices, and file handles are not additional fields in the current saved board settings.

Normalization also occurs while creating loaded portfolio records, so some changes happen in memory on import, before a later save. Do not rely on validation alone to guarantee that a file’s data survives unchanged. Keep custom data under your own extension namespace, for example extensions.acme, and maintain your own references to task IDs.

Authoring and validation checklist

  1. Start with the empty-board example and use numeric schemaVersion 1 and the exact appId.
  2. Use the canonical four columns and match every task status to one of them.
  3. Supply all required task keys. Use unique safe-integer task IDs, real dates, and ISO timestamp strings with timezones.
  4. Represent missing priority/effort as null, missing dates and references as empty strings, and empty collections as arrays.
  5. Include a reason for blocked tasks; keep checklist and attachment records to their exact key sets.
  6. Use valid roadmap IDs and ensure references exist. Keep date ranges chronological.
  7. Use extensions for custom data. Only provide timeline history when you have coherent snapshots and events; an empty extensions object is valid.
  8. Import a copy into the app, save it, and compare the resulting JSON. Inspect tags, references, attachments, columns, and compatibility fields for normalization changes.
Typical failureCause / correction
Invalid task structureRequired property missing or unknown property added. Use the task field tables.
Task status is invalidTask status does not exactly match an input column.
Blocked tasks require blockerReasonProvide a non-empty reason when blocked is true.
Invalid extensions.roadmap structureMissing one of the three arrays, extra properties, duplicate IDs, or malformed/missing dates.

The application uses a JavaScript validator, not a bundled JSON Schema document. These tables describe that implementation, including its weaker checks. The recommended authoring rules are intentionally stronger where the application assumes uniqueness, valid dates, or consistent history without validating them.
