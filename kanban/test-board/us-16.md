# US16 · Workitem tabs and direct updates

Scope: [feedback on issue #39](https://github.com/sebastiaofv/TeamOs/issues/39#issuecomment-6590507276). Import [us-16.board.json](us-16.board.json) as a writable project.

Edit-mode follow-up: [remove attachments from the edit form](https://github.com/sebastiaofv/TeamOs/issues/39#issuecomment-6591349062). Open **Files and todo → Edit**, then repeat using the card's edit action: the form has no attachment section, uploader, file picker or file list. Change the title and save; reopen **Attachments** and confirm all three original files, upload dates and authors are preserved. Add and remove a file directly in that tab, without **Edit**. Canceling a content edit also leaves attachments unchanged.

First-change follow-up: [attachment immediately after import](https://github.com/sebastiaofv/TeamOs/issues/39#issuecomment-6620443516). Start a fresh browser session and import the board using **Import Projects**. Without making any other changes, open **Files and todo → Attachments → Add Files**. When Chromium requests permission to change the project JSON, allow it, then select a TXT file or image. The file is added, recorded in History and saved automatically; reopen the JSON to verify its contents, date and uploader. Repeat with a large accepted file. Denying write permission shows a clear message and leaves the project unchanged; clicking Add Files again can retry. Canceling the attachment picker also leaves the project unchanged.

For a project containing completed workitem transfers, an unrelated attachment save failure must show the project’s **Save failed / Retry** state without presenting **Pending transfers** for the old completed operation. Retrying the save preserves the attachment. Genuine unfinished transfers, including a failed final receipt write, must still offer **Resume transfer** and finish without creating another workitem.

1. Create a workitem. The form contains its details and properties, with no attachment fields. Save it and open **Attachments**: set the local uploader name and add a TXT file or image directly, without **Edit** or another Save. It appears in the table and persists after reopening/reimport.
2. Open **Files and todo → Attachments**. The initial order is **new.txt**, **middle.txt**, **old.txt**, newest first. The legacy file shows **Unknown**. Existing dates and authors remain unchanged after adding a new file.
3. Download an attachment. Remove one and cancel the confirmation: the row remains. Repeat and confirm **Remove**: only that file disappears. Check History for the attachment change.
4. Add the same file twice: the duplicate is skipped with a warning. Select 11 small files: accept up to the 10-file workitem limit. Select a file larger than 10 MB: reject it without changing existing files.
5. In **Files and todo → Details**, check/uncheck an existing todo directly. The count updates, the change persists, and History records it. Adding or editing todo text still requires **Edit**.
6. In **Relations**, read the complete **ABC-TK-123456** ID and open it. There is no repeated “Relations” heading above the groups. **Pull Requests** also has no repeated heading; its add/edit controls still work.
7. Open **No files → Attachments**. The empty message and upload controls appear. Switch tabs and use Left/Right, Home and End in the tab bar.
8. Import without write permission and inspect a historical timeline position: attachments stay downloadable, but upload/removal controls are absent and todo checkboxes are disabled. The historical view contains only the data present at that time.
9. Repeat in Portuguese, light/dark themes, and at 390px width. Relation IDs remain readable; attachment tables scroll within the dialog where necessary.

Uploader names are local attribution, shared with the last-used comment author (Anonymous initially). Existing attachments without uploader metadata remain compatible and display Unknown.
